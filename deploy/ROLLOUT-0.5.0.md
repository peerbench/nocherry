# Rolling out object format 0.5.0

Spec: `docs/nocherry-commit-reveal-spec-v0.5.md`. Servers accept `0.2.0` and `0.5.0` side by side; verifiers dispatch on `spec_version`; nothing about `0.2.0` objects changes.

## Order

A server built before this change drops the unknown fields of a 0.5.0 commitment while parsing and answers `Missing required field: reveal_probability`. Clients must therefore not default to 0.5.0 before every registry server lists it.

1. Core and WASM (this branch). `cargo test --workspace`, `npm run build:wasm`, `npm run build`.
2. Regenerate the vendored WASM glue of every deployment target: `node deploy/scripts/regen-wasm.mjs` (`--check` reports stale files without writing). Commit the result.
3. Deploy servers, each with its storage migration (below). The migration adds two nullable columns and a unique index; existing rows are untouched.
4. Confirm each server: `GET /v1/server-info` lists `"spec_versions_accepted": ["0.2.0", "0.5.0"]`, `max_items`, `max_metadata_bytes`. Submit one 0.5.0 commitment with `pb-js commit <dir> --format 0.5.0` and `pb-js submit <dir>`; the receipt must carry `selection.reveal_probability_ppm` and verify with `pb-js verify <dir>/server-receipts.json`.
5. Only then switch the client default: `DEFAULT_FORMAT` in `packages/pb-js/src/format.ts` to `FORMAT_V5`, update the CLI tests that pin `0.2.0` as the default, and release `@nocherry/sdk`. Until then users opt in with `--format 0.5.0` or `PB_FORMAT=0.5.0`.
6. `packages/pb-demo` and the Rust `pb-cli` still create 0.2.0 commitments; move them after the servers.

## Per target

### Cloudflare Workers (`deploy/cloudflare`)

- Glue: `deploy/cloudflare/src/wasm/pb_wasm.js` and `.d.ts` are regenerated by the script; `deploy.js` copies `pkg/pb_wasm_bg.wasm` at deploy time. Build that binary without BLS first: `npm run build:wasm:server` writes to `pkg-server/`, or run `npm run build:wasm` and accept the larger default-features binary. `deploy.js` reads `pkg/`.
- Database: `npx wrangler d1 migrations apply commit-reveal-db` applies `migrations/0002_stream_index.sql` (two `ALTER TABLE ADD COLUMN`, one unique index). D1 has no `ADD COLUMN IF NOT EXISTS`; wrangler tracks applied migrations, so run it once.
- Deploy: `node deploy.js` or `npx wrangler deploy`.

### Google Cloud Run (`deploy/google-cloud`)

- Glue and binary: `src/wasm/pb_wasm.js`, `.d.ts`, `pb_wasm_bg.wasm` regenerated by the script (vendored, no deploy-time copy).
- Firestore: the new `streams` collection needs the composite index in `firestore.indexes.json` (`signing_key`, `stream_id`, `sequence`); deploy indexes before the service: `gcloud firestore indexes composite create` or `firebase deploy --only firestore:indexes`. Stream uniqueness is a `create()` of a deterministic document id inside the same transaction as the commitment, so no migration of existing documents is needed.
- Deploy: `node deploy.js`.

### Supabase Edge Function (`deploy/supabase`)

- Glue: `wasm/pb_wasm.js`, `.d.ts`, `pb_wasm_bg.wasm`, the base64 `pb_wasm_bg.ts` and the export list in `mod.ts` are regenerated by the script (`setup.sh` step 2 calls it).
- Database: `supabase db push` applies `migrations/00003_stream_index.sql`.
- Deploy: `supabase functions deploy commit-reveal`.

### PGlite (`deploy/pglite`)

Uses `@nocherry/storage` through `packages/pb-node`; the Postgres schema in `packages/storage/src/postgres.ts` adds the columns with `ADD COLUMN IF NOT EXISTS` on connect. No separate step.

### Reveal publishing helper (`dev-reveal-publishing-helpers/cloudflare-r2`)

Its hand-written WASM wrapper is replaced by generated glue with the same loading model. It only calls `verifyCommitment`, which now accepts both formats. Redeploy with `npx wrangler deploy` in that directory. Not exercised by the test suites; check `POST /v1/upload` with a 0.5.0 receipt after deploying.

## What a 0.5.0 deployment changes for operators

- Receipts of commitments in a stream carry `stream_activity`; `GET /v1/streams/{signing_key}/{stream_id}` is public and signed.
- `POST /v1/commitments` answers `409 stream_sequence_taken` with the existing hash when a key reuses a stream name and sequence. This is the intended behavior (spec v0.5 12.2), not a storage error.
- `max_items` (default 100000) and the 4096-byte metadata cap are enforced; set `maxItems` in the config to change the former.
- Reveal data verification compares fetched bytes with the opened plain hash; an item that no registered reveal has opened reports `not_opened` in `verify-publication`.

## Not done here

- No server was deployed and no production database was migrated. Everything above was run locally against SQLite and in-process Hono apps; D1, Firestore and Supabase adapters were changed in code and type-checked where tooling allowed, not executed.
- The client default is still 0.2.0 (step 5).
